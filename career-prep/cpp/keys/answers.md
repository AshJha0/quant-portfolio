## What does it print

- **C01** Prints `ctor move dtor ctor copy dtor dtor dtor`. `make()` returns a prvalue, so no copy or move happens inside it (guaranteed elision since C++17, [class.copy.elision]); `push_back` binds that temporary to `T&&` and move-constructs the element, then the temporary dies. `emplace_back()` constructs in place. `T a = v[0]` copies. At the end of `main`, `a` dies first (reverse order of construction), then the vector destroys its two elements. Because of `reserve(2)` there is no reallocation; without it, the second insertion would have moved (the move constructor is `noexcept`) the first element.
- **C02** Prints `B D D B`. During the base constructor the object is a `B`, so the virtual call resolves to `B::hello` ([class.cdtor]); the same holds in reverse during destruction. Calling virtuals from constructors does not reach the derived override, which is why "init()" hooks need a two-phase construction or a factory.
- **C03** Prints `A B A A`. Passing by value, assigning to an `A`, and storing in `std::vector<A>` all copy only the `A` part (slicing), and the copy's vtable pointer is `A`'s. Only the reference keeps dynamic dispatch. Store `std::unique_ptr<A>` for a polymorphic container.
- **C04** Prints `not-less 0 1 4294967295`. In `i < u` the `int` is converted to `unsigned` ([expr.arith.conv]), and -1 becomes 4294967295. `c += 1` computes 256 as `int` and converts back, which wraps modulo 256 (well defined for unsigned). `'a' + 1` promotes `char` to `int`. Unsigned subtraction wraps modulo 2^32. GCC's `-Wsign-compare` flags the first line; that is why the repository builds with warnings as errors.
- **C05** Prints `b a x ~x ~a ~b`. Members are initialised in declaration order, whatever order the initialiser list is written in ([class.base.init]); GCC's `-Wreorder` warns. Destruction is the exact reverse: locals first (`x`), then members in reverse declaration order.
- **C06** Prints `int long T T double`. `f(1)` and `f(1L)` are exact matches for the non-templates, which win ties against the template. `1.0f` and `'a'` would need a promotion to reach `double` or `int`, but the template deduces `T = float` / `T = char` as an exact match, and exact beats promotion. `f(1.0)` is an exact match for both `f(double)` and `f<double>`; on a tie, the non-template wins ([over.match.best]).
- **C07** Prints `copy move end`. `std::move(a)` on a `const T` yields `const T&&`, which cannot bind to `T&&`, so the copy constructor is chosen: moving from a `const` object silently copies. `T(T(T()))` is a prvalue initialising `d` directly, with no copy or move at all (guaranteed elision).
- **C08** Prints `24 16 64 1 4`. `A` is `char` (1) + 7 padding + `double` (8) + `char` (1) + 7 tail padding = 24; ordering members by decreasing alignment gives `B` = 8 + 1 + 1 + 6 padding = 16. `alignas(64)` makes size a multiple of 64. An empty class has size 1 so distinct objects have distinct addresses. `[[no_unique_address]]` lets the empty member overlap `x` (GCC and Clang honour it; MSVC needs `[[msvc::no_unique_address]]`). These sizes are for the x86-64 System V ABI.
- **C09** Prints `2 1 0 1 0 1`. Two `shared_ptr`s share ownership (the `weak_ptr` does not count). After `q.reset()` one owner is left and the object lives, so `expired()` is false; after `p.reset()` it is destroyed. A `unique_ptr` converts to a `shared_ptr` by move, leaving the `unique_ptr` empty and a use count of 1.
- **C10** Prints `6 -4 2 6765`. `(t + ... + 0)` is a binary right fold. `(... - t)` folds left: (1 - 2) - 3 = -4. `(t - ...)` folds right: 1 - (2 - 3) = 2. `fib(20)` = 6765; the `static_assert` shows the function also runs at compile time.
- **C11** Prints `5 3 1 3 5 2 1`. `std::remove` only moves the kept elements to the front and returns the new logical end; the size is still 5 and the tail holds unspecified (moved-from) values. `erase(it, end)` shrinks it to `1 3 5`. C++20 `std::erase(w, 4)` does both and returns the number removed, 2.

## Write it

- **C12** See [`unique_ptr.hpp`](../solutions/unique_ptr.hpp). Points to make: copy operations deleted; moves `noexcept` (so containers move rather than copy on growth); `reset` assigns the new pointer before deleting the old one, so a destructor that reaches back into the owner sees a consistent state; `operator=(UniquePtr&&)` as `reset(o.release())` is self-move safe for free. Checked by `check_single.cpp` (live-object counting under ASan, plus `static_assert`s that it is non-copyable, nothrow-movable and pointer-sized).
- **C13** See [`spsc_ring.hpp`](../solutions/spsc_ring.hpp). The producer reads its own `head_` relaxed (only it writes it), reads `tail_` with acquire (so the consumer's read of a slot happens before the producer overwrites it), writes the slot, then stores `head_` with release (publishing the slot). The consumer is the mirror image. Free-running unsigned indices make `head - tail` the fill level and use all N slots; `alignas(64)` keeps the two indices on separate cache lines. Checked by `check_threads.cpp`: 200,000 values through a 64-slot ring must arrive in order under ThreadSanitizer. Weakening the producer's release store to relaxed makes ThreadSanitizer report a data race on the slot (tried while writing this pack).
- **C14** See [`blocking_queue.hpp`](../solutions/blocking_queue.hpp). `wait` with a predicate handles spurious wake-ups and the lost-wake-up race; notify after releasing the lock; `close` uses `notify_all` so every waiter re-checks. Checked with 4 producers and 4 consumers moving 80,000 numbers: the count and the sum must be exact.
- **C15** See [`object_pool.hpp`](../solutions/object_pool.hpp). Each slot is a union of a free-list link and raw storage aligned for `T`; `create` pops a slot and placement-news into it; `destroy` calls the destructor explicitly and pushes the slot back. If the constructor throws, the slot goes back on the list before rethrowing. Checked for exhaustion, LIFO reuse, the throwing constructor, and no leaks under ASan.
- **C16** See [`spinlock.hpp`](../solutions/spinlock.hpp). The inner loop spins on a relaxed load (shared cache line, no bus traffic) and only tries the `exchange` when the lock looks free; `_mm_pause` eases the pipeline and the sibling hyper-thread. Acquire on lock, release on unlock. Checked with 4 threads incrementing a plain `int64_t` 200,000 times under ThreadSanitizer. Spinlocks suit very short critical sections on pinned threads; otherwise prefer a mutex.
- **C17** See [`thread_pool.hpp`](../solutions/thread_pool.hpp). `std::packaged_task` carries the result or exception into the future; it is move-only, so it is wrapped in a `shared_ptr` to fit `std::function`. Workers are `std::jthread`s declared after the queue, so they are joined before the queue is destroyed. Checked with 1,000 tasks (sum of squares = 333,833,500) and one throwing task.
- **C18** See [`fixed_price.hpp`](../solutions/fixed_price.hpp). In binary floating point 0.1 is not representable, so ten additions of 0.1 give 0.9999999999999999, not 1 (Goldberg, "What every computer scientist should know about floating-point arithmetic", ACM Computing Surveys 23(1), 1991); the check program asserts both this and that the fixed-point sum is exactly 1. Overflow detection uses `__builtin_add_overflow` / `__builtin_mul_overflow` (GCC and Clang). Printing `INT64_MIN` needs the magnitude in unsigned arithmetic, since `-INT64_MIN` overflows.
- **C19** See [`seqlock.hpp`](../solutions/seqlock.hpp). A plain `memcpy` of the payload while the writer writes is a data race, and so undefined behaviour, even if the reader discards the result. Storing the payload as atomic words removes the race; publishing each word with release and reading with acquire makes a reader that sees any new word also see the odd sequence number, so its re-check fails (Boehm, MSPC 2012). Checked under ThreadSanitizer: 100,000 writes of `{i, 3i, 7i}` while a reader asserts it never sees a torn or backwards value. Limit of the check: on x86 the hardware keeps stores in order, so weakening those release stores to relaxed still passes here; the argument above, not the test, is what makes the code correct on weaker hardware such as Arm.
- **C20** See [`concepts.hpp`](../solutions/concepts.hpp). A `requires` expression lists the operations the template body uses, so a bad call fails at the call site with a readable message rather than deep inside the body. `alignas(64)` on the counter makes both its alignment and its size 64, so array neighbours are 64 bytes apart (checked with `static_assert` and pointer arithmetic).

## Explain it

- **C21** `relaxed`, `consume` (discouraged; compilers treat it as acquire), `acquire`, `release`, `acq_rel`, `seq_cst`. In C13 each side has three atomic operations: a relaxed load of its own index (no other thread writes it, so no ordering is needed), an acquire load of the other side's index, and a release store of its own index. If the release store were relaxed, the consumer could see the new `head_` before the slot contents; if the acquire load were relaxed, the consumer could read the slot before the data written to it. Either way it reads garbage. On x86 the hardware gives acquire and release for free on plain loads and stores, so such bugs often hide until the code runs on Arm or the compiler reorders.
- **C22** The usual suspects: heap allocation on the hot path (allocator locks and page faults); system calls and logging that write synchronously; page faults on first touch (pre-fault and lock memory with `mlock`); the thread being descheduled or migrated (pin it with `taskset`/`isolcpus`, use a real-time policy); cache and TLB misses from pointer-chasing structures; branch mispredictions on rare paths; lock contention; interrupts landing on the core; frequency scaling and deep C-states. To find them: timestamp at stage boundaries with `rdtsc` and plot the tail, not the mean; `perf stat` for misses and context switches; `perf record` on the slow events; a histogram per stage to see which one owns the tail.
- **C23** Two threads write different variables that sit on the same 64-byte cache line, so the line ping-pongs between their cores even though no data is shared. To show it: time N threads each incrementing their own counter in an array of plain `uint64_t`, then in an array of `PaddedCounter`; on a multi-core machine the padded version scales and the packed one does not (`perf c2c` reports the contended line directly). Padding to the line size gives each counter its own line. C++17 names the size `std::hardware_destructive_interference_size`, but GCC warns that its value can differ between compiler flags, so fixed code often uses 64 directly.
- **C24** A virtual call is an indirect call through the vtable: cheap when predicted, but it blocks inlining. CRTP resolves the call at compile time, so it inlines, but every concrete type is a different static type and cannot share one container. `std::variant` plus `std::visit` keeps a closed set of types in one value with no heap allocation and usually compiles to a jump table; adding a type means touching every visitor. Rule of thumb: an open set of types extended by others, virtual; a fixed set on a hot path, `variant`; static composition or policy classes, CRTP. Measure before choosing; the indirect call is rarely the bottleneck compared with cache misses.
