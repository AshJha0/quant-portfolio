# Equity VaR Engine (Rust)

A dependency-free Rust port of the Python library
[`python/equity/03-var-es-engine`](../../python/equity/03-var-es-engine)
(`eq_var`), alongside [`cpp/equity-var-engine`](../../cpp/equity-var-engine).
It computes historical, parametric and Monte Carlo VaR and ES for a book of
dollar exposures to equity factors, and backtests the forecasts. European
options on those factors are repriced in full in every historical or Monte
Carlo scenario (see [Option VaR](#option-var-full-revaluation)).

The conventions are shared with every VaR engine in the repository and are
checked by the shared `conv_*` goldens (see `docs/METHODOLOGY.md` section 0):

- `alpha` is the tail probability (`0.01` = 99 % VaR); `alpha` outside
  `(0, 0.5)` is an error.
- Empirical VaR is the order statistic `L(m)`, `m = ceil(n alpha - 1e-9)`,
  with no interpolation. ES is Acerbi-Tasche with the exact fractional atom.
- Kupiec and Basel take a struct with named fields; the Basel zone follows
  the window and `alpha`.
- Bad input (NaN, infinities, empty, too short, negative where invalid)
  returns `Err`, never a number. A proptest walk over every public function
  checks this.

```
returns panel (T x n) -- sample / EWMA covariance -- cholesky_repair (jitter, Clip, Higham)
   |
   +-- Historical VaR -- plain / BRW age-weighted / filtered per factor (S9)
   +-- Parametric VaR -- normal / variance-matched Student-t / Cornish-Fisher (alpha-aware check)
   +-- Monte Carlo ----- normal and multivariate t; one simulation gives VaR, ES, bootstrap SE
   +-- Expected Shortfall -- Acerbi-Tasche / closed forms
   +-- Backtests ------- Kupiec, Christoffersen, Basel (any window), Acerbi-Szekely Z2
```

## Quickstart

From `rust/` (the Cargo workspace root; one `Cargo.lock`, one `target/`):

```sh
cargo test --release --locked -p eq-var-engine
cargo clippy --release --all-targets --locked -p eq-var-engine -- -D warnings
cargo run --release --locked -p eq-var-engine --bin bench -- --out /tmp/bench.json
```

The tests are 138 integration tests and 16 doctests. Without `--out` the
bench writes `bench/results.json` in this crate.

The Philox4x32-10 path streams, the xoshiro256++ stream (still used outside
the MC VaR), the Acklam guess and the Cholesky kernel come from
the workspace's [`qp-core`](../core) crate (std only).

```rust
use eq_var_engine::prelude::*;

let v_h = historical_var(&pnl, 0.01)?;                             // order statistic
let v_f = filtered_historical_var_factors(&panel, &w, 0.01, 0.94)?; // per-factor FHS
let v_p = parametric_var(&w, &cov, 0.01, TailModel::StudentT { df: 6.0 })?;
let run = monte_carlo_run(&w, &cov, 0.01, 100_000, TailModel::Normal, 42, 200)?;
// run.var, run.es, run.se (bootstrap), run.se_kde, run.jitter
let k = kupiec_pof(&KupiecInput { n_obs: 250, n_exceptions: 5, alpha: 0.01 })?;
let tl = basel_traffic_light(&BaselInput { n_obs: 250, n_exceptions: 5, alpha: 0.01 })?;
// tl.zone == Yellow, tl.multiplier == 3.40
```

  each failed on the old code first.

  test fails if a new `pub fn` has no entry.
- MC against closed forms: normal MC VaR within SE bars of the
  parametric VaR, simulated covariance against the target.

## Allocation-free API (`fast`)

`eq_var_engine::fast` holds the hot paths for latency-sensitive callers.
Each function returns the same `f64` bits as its main-API counterpart.
It allocates nothing on the success path and never panics. Errors are a
`Copy` enum, `VarFault`, with no `String`.

| fast function | main API counterpart | scratch |
|---|---|---|
| `historical_var_ws` | `historical_var` | `&mut [f64]`, len >= n |
| `expected_shortfall_ws` | `expected_shortfall` | same |
| `empirical_var_es_ws` | `tail::empirical_var_es` | same |
| `var_bootstrap_se_ws` | `var_bootstrap_se` | `buf` len >= n, `est` len >= n_boot |
| `portfolio_sigma_fast` | `portfolio_sigma` | none |
| `parametric_var_fast` / `parametric_es_fast` | `parametric_var` / `parametric_es` | none |
| `McWorkspace::run` / `::var` | `monte_carlo_run` / `monte_carlo_var` | the workspace |

`McWorkspace::new(n, max_paths, max_boot)` sizes the buffers.
`prepare(cov, tail)` factors the covariance once; this step allocates.
After that, `run` and `var` allocate nothing. The workspace revalues the
book path by path and never builds the `n_paths x n` scenario panel.

`tests/test_fast_equiv.rs` checks bit equality with the main API.
`tests/test_fast_alloc.rs` counts heap allocations with a global allocator
and requires zero for every call above.

Since milestone v2.1 the MC draw is threaded: each path has its own
Philox4x32-10 stream with AS 241 normals, so the bits are the same on any
thread count and match the C++ engine. The bootstrap SE is threaded the
same way. At 10k paths x 50 factors the main API is 4.7x faster than in
2.0.0 on a 12-thread laptop (CHANGELOG, milestone v2.1; one laptop run, not a CI
figure).

## Latency

`cargo run --release --bin bench` times each kernel call by call after a
warm-up, over 16 rotating inputs, and writes `bench/results.json`. Calls
under a few microseconds are timed in batches of K and divided by K. The
main-API rows are the "before" numbers (that code is unchanged). The
`fast` rows are the "after" numbers.

Numbers from this machine: Intel Core 5 120U, WSL2 on Windows 11,
rustc 1.99.1, release profile (opt-level 3, fat LTO, one codegen unit),
2026-11-01. WSL2 adds scheduler jitter, so read p99.9 and max as upper
bounds. Sibling builds shared the machine during the run.

> **How these figures were timed.** Old harness: `std::time::Instant` over a fixed batch per sample (16 or 64 calls for fast kernels, 1 for slow ones). They are one laptop run (Intel Core 5 120U, WSL2) kept for the record; `bench/results.json` holds the same run. Benches now use one method in C++ and Rust: a batch of back-to-back calls sized to at least 2 us per sample, median with p10/p90 ([docs/BENCHMARKS.md](../../docs/BENCHMARKS.md)). Current figures, measured base against head on one CI runner, are in the `bench-results` artifact of the [CI bench job](https://github.com/AshJha0/quant-portfolio/actions/workflows/ci.yml).

| kernel | before p50 / p99 / p99.9 ns | after p50 / p99 / p99.9 ns |
|---|---|---|
| historical VaR, n = 250 | 725 / 2 358 / 6 323 | 541 / 1 786 / 4 139 |
| historical VaR, n = 1000 | 2 456 / 5 175 / 16 079 | 1 968 / 5 608 / 15 948 |
| empirical ES 97.5 %, n = 250 | 737 / 2 208 / 7 360 | 581 / 893 / 4 109 |
| parametric VaR normal, 100 assets | 9 504 / 29 060 / 64 916 | 5 502 / 15 222 / 46 006 |
| parametric VaR t(6), 100 assets | 16 866 / 47 069 / 111 335 | 13 468 / 31 496 / 66 041 |

| MC VaR only, 20 factors x 10k paths (old serial stream) | 5.83 / 9.05 / 9.96 ms | 3.91 / 10.4 / 11.9 ms |

Where the time goes:

- Historical VaR and ES: the gain is the removed loss-vector allocation.
  The selection itself (`select_nth_unstable`) is the floor.
- Parametric: `w' S w` runs four matrix rows side by side. Each row keeps
  its own left-to-right sum, so the bits match `Matrix::matvec`. The
  finite check over the covariance and the t quantile solve are the rest.
- MC (old serial stream, as timed above): the Box-Muller draws (`ln`, `sqrt`, `sin`, `cos`) dominated; the MC rows predate the Philox rewrite and are kept as the recorded "before" run. The
  workspace saves the panel allocation and the second pass over it.

Vectorisation (`RUSTFLAGS=-Cremark=loop-vectorize`, LTO off so remarks
print): the negate-and-copy and finite-check loops vectorise (SSE2, width
2). The dot products, the `L z` product and the sums do not: LLVM may not
reorder floating-point adds, and reordering would change the bits.
Selection and sort loops branch on data and do not vectorise.

## Option VaR (full revaluation)

`option_reval` prices European options by Black-Scholes-Merton with a
dividend yield, gives closed-form Greeks and full-revaluation and
delta-gamma P&L, mirroring `eq_var.revaluation`. Two functions put it into
the VaR pipeline:

- `historical_option_var_es(legs, exposures, factor_returns, alpha, dt)`
  returns `(VaR, ES)` with each of the `T >= MIN_OBS` historical rows as a
  scenario: every leg repriced at `S e^x` with `tau - dt` left, plus the
  linear `exposures . r`.
- `monte_carlo_option_run(legs, exposures, cov, alpha, n_paths, tail, seed,
  n_boot, dt)` returns an `McRun` from the same simulation as
  `monte_carlo_run`, repriced path by path.

Options are held at today's implied vol unless you use the `_vol` drivers
below. The linear legs
use `exposures . r` on log returns, as the rest of this crate does.

Vol scenario modes. `full_revaluation_pnl_vol_mode(legs, x, dv, n_factors, dt, mode,
skews)` takes `VolMode::StickyStrike` (`sigma + dv`), `StickyDelta`
(`sigma - skew x + dv`, `skews` one per leg or empty) or `HistoricalAtm`
(`sigma e^{dv}`, `dv` a historical log change of ATM vol). `full_revaluation_pnl`
is sticky strike. All three are pinned to the Python reference at
1e-12 relative (`vol_modes_golden` in `tests/test_option_reval.rs`).

The VaR drivers take vol scenarios too, on what we call the combined axis.
The plain idea: a vol shock is just one more risk factor, so it goes in the
same panel (or covariance) as the spot returns, after them. Formally, with J
spot factors the panel has 2J columns: spot log returns in columns 0..J-1,
then the vol shock of factor j in column J + j (vol points for sticky strike
and sticky delta, a log change of ATM vol for historical ATM).
`exposures` and `leg.factor` still index the J spot factors. For Monte Carlo
the covariance is 2J x 2J, so the spot-vol correlation (the leverage effect,
usually negative for equities) is simulated, not assumed away. With sticky
strike and an all-zero vol block every driver gives the old answer bit for
bit. Worked example: the two-leg test book with vol shocks of a few vol
points a day has 99 % historical VaR 39.22 sticky strike, 39.86 sticky delta
(skews -0.1, -0.2) and 34.80 historical ATM, against 33.44 with vol held
fixed; all three match Python at 1e-11 relative.
Entry points: `option_book_pnl_vol`, `historical_option_var_es_vol` and
`monte_carlo_option_run_vol` in `option_reval`; tests in
`tests/test_option_var_vol.rs`.

Parity with Python. The historical numbers are pinned to the Python
reference (`eq_var.revaluation.full_revaluation_pnl` followed by the S2 order
statistic) at 1e-11 relative, for an options-only book and for options plus
a linear book, with and without ageing (`dt = 1/252`). The goldens come from
[`cpp/equity-var-engine/tools/gen_option_var_golden.py`](../../cpp/equity-var-engine/tools/gen_option_var_golden.py),
which builds a closed-form scenario panel so no RNG is shared. Monte Carlo
cannot match numpy draw for draw, so its test uses a case with a known
answer: a long call on one normal factor has P&L monotone in the factor, so
the exact VaR is minus the P&L at sigma z_alpha and the exact ES is a
one-dimensional integral. The engine must land within 4 bootstrap standard
errors (ES within 2 %). A book with no option legs goes down the unchanged
linear path, and the tests check the two give identical bits.
