# Methodology

Rust FX VaR/ES engine, mirroring the Python reference
`python/fx/03-var-es-engine` (`fx_var`) and the C++ twin
`cpp/fx-var-engine` (`fxvar`). This document covers **why the Rust twin
exists**, the model choices (with alternatives and trade-offs), and the
assumptions register. The mathematical derivations shared with the Python
package are not repeated in full — the Python `docs/METHODOLOGY.md` is the
primary reference for the underlying models; this file states where the
Rust engine follows it and where it deliberately differs (chiefly from the
C++ engine, which it mirrors module-for-module).

---

## 1. Why a Rust engine for FX risk?

**1.1 Intraday multi-currency books.** An FX desk's book turns over
continuously: spot fills, forward rolls, cross hedges. Risk that is
recomputed only in the overnight batch is stale by 08:05. The compiled
book (struct-of-arrays legs, one `exp()` per leg per scenario) revalues a
250-position / 50-factor book under 500 historical scenarios in a few
milliseconds and runs a 100k-path full-revaluation Monte Carlo in around a
second on one core — fast enough to recompute VaR, ES and the full stress
library on every material fill, not once a day.

**1.2 Memory-safe production compute.** A risk engine that panics or
corrupts memory on a malformed book is a worse outcome than a slow one.
Rust's ownership model and `Result`-everywhere API give the same
determinism and throughput as the C++ engine with no undefined-behaviour
surface (`#![deny(missing_docs)]`, no `unsafe`, borrow-checked struct-of-
arrays revaluation) — attractive for teams that want the C++ twin's speed
without its memory-safety burden, or a second, independently-implemented
engine to cross-check the C++ one against.

**1.3 Regression-gated triplet with the research stack.** The Python
package is where methodology evolves (it also carries the Garman–Kohlhagen
options layer); the C++ and Rust engines are two independent
production-shaped implementations of the same linear (spot/forward)
subset. The contract between all three is executable: golden constants
generated by the Python package are committed in
`tests/test_golden_python.rs` (and independently in the C++ suite) and any
semantic drift on either side breaks its own build — see
`docs/VALIDATION.md` §3.

**Alternatives considered.**
- *Stay in Python/NumPy*: adequate for overnight batch on one book; loses
  intraday latency, per-fill recompute, and deployment determinism. Kept
  as the research/reference stack.
- *C++*: comparable performance; already the primary production twin in
  this portfolio. Rust is chosen here as a second implementation with a
  different failure-mode profile (no null/dangling-pointer class of bugs,
  exhaustive `Result` handling checked by the compiler) — useful both as a
  standalone deployment target and as an independent cross-check of the
  C++ engine's numbers.
- *GPU MC*: unnecessary at this factor count — the 100k×50 problem is
  sub-second-to-low-seconds on one core; GPU pays off only for
  path-dependent exotics.

## 2. Factor model and book representation

Identical to the Python reference (`fx_var.common`, `fx_var.book`) and the
C++ engine (`fxvar::Book`, `fxvar::CompiledBook`):

- Pairs are quoted BASE/QUOTE (EURUSD = USD per 1 EUR), per the
  portfolio-wide FX conventions.
- Every currency is represented by one **USD factor**: `FX:CCY` is the
  daily log return of CCYUSD (USD price of 1 unit of CCY). USD has no
  factor. Cross pairs are **triangulated**: a EURJPY position becomes a
  long-EUR leg and short-JPY leg. There is no separate cross factor, so
  the factor set is arbitrage-consistent by construction and cross vol/
  correlation are consequences of the USD-leg covariance — the identity is
  tested to 1e-12 (`book::tests::triangulation_identity_eurjpy`).
- `IR:CCY` is an absolute shock (decimal p.a.) to the continuously
  compounded ACT/365 zero rate, flat curve per currency.
- **Forwards** are spot plus two deposit legs:
  `V_usd = N e^{−r_f T} S_f − N K e^{−r_d T} S_d`. Forward points are
  therefore *derived* from the two rate factors (CIP), not an independent
  factor; the position responds to both FX and both IR factors. Tested:
  zero value at CIP inception, equality with the discounted cash legs,
  closed-form rate sensitivities, and the T→0 edge case (rate-factor
  sensitivity collapses to zero — `edge_cases.rs`).
- **P&L convention**: profit(+)/loss(−) in the book's base currency,
  `PnL = V1_usd/S1_base − V0_usd/S0_base` with the base currency's own USD
  price shocked consistently. A base-ccy cash balance has exactly zero
  risk (tested).
- **Options are out of scope**, mirroring the C++ engine, and stay in the
  Python stack (Garman–Kohlhagen full reval / Greek mapping). This keeps
  the hot path branch-free and log-linear per leg; on the linear subset
  all three stacks are exactly comparable, which is what the
  cross-language golden tests exploit.

### Hot path

`CompiledBook` flattens every position into USD legs at construction:
per-leg unshocked discounted value `v0 = amount · S0 · e^{−r0 T}`, an FX
factor index, an IR factor index and `−T`. A scenario revalues each leg as
`v0 · exp(dfx − T·dr)`. The struct-of-arrays layout (`Vec<f64>` /
`Vec<i64>` parallel arrays) keeps the scenario loop a straight stream over
contiguous memory: no dynamic dispatch, no hash-map lookups inside the
loop, no per-scenario allocation. Default strikes/entry rates resolve
against the reference market once, at compile time
(`CompiledBook::new`). See `src/bin/bench.rs` for throughput.

## 3. VaR methods (choices and trade-offs)

Same estimator suite as the Python/C++ references; see the Python
`docs/METHODOLOGY.md` for full derivations and citations (BRW 1998;
Barone-Adesi et al. 1999; Maillard 2012; Acerbi–Tasche 2002).

- **Historical simulation** (plain / BRW age-weighted / filtered): full
  revaluation under empirical scenarios; FHS devolatilises by per-factor
  EWMA sigma and rescales to today's forecast — the variant that survives
  volatility-clustering backtests. Chosen as the primary desk method
  because it imposes no distributional shape on FX returns.
- **Parametric var-covar**: finite-difference linearisation
  (`CompiledBook::linear_exposures`) + normal or standardised Student-t
  overlay on the same sigma (so tail comparisons are at equal risk), plus
  Cornish–Fisher with an explicit monotonicity domain check (outside the
  domain the expansion is refused, not silently wrong). Chosen for speed
  and attribution (exposure vector is a by-product); limitation: linear in
  the factors.
- **Monte Carlo**: normal / covariance-matched t / jump-mixture with full
  revaluation. The jump-mixture (common Bernoulli event, per-ccy jump
  size) is the *peg-break overlay*: it deliberately adds variance the
  covariance matrix cannot contain. Chosen as the only method that can
  price risks absent from history.
- **ES throughout** (Acerbi–Tasche weighted tail-splitting empirical
  estimator; closed forms for normal/t): coherent, sees tail sizes — the
  Basel FRTB headline measure, and the right measure for books with
  jump-to-default-like peg risk.

### Alpha convention

`alpha` is a **confidence level** (`0.99` = 99% VaR) throughout this
crate, matching the Python/C++ FX engines exactly — note this is the
*opposite* convention from the sibling `equity-var-engine` Rust crate,
which uses `alpha` as a tail probability (`0.01` = 99% VaR). This is
called out prominently in `src/lib.rs` because it is the single easiest
cross-crate mistake to make in this portfolio.

## 4. Assumptions register

Each assumption states what breaks if violated. A1–A8 mirror the
Python/C++ references; A9–A10 are Rust-specific.

| # | Assumption | What breaks if violated |
| --- | --- | --- |
| A1 | USD-factor triangulation: cross risk fully captured by the two USD legs. | If a cross trades away from triangulated parity (capital controls, CNH vs CNY), cross P&L is misstated; add the offshore ccy as a separate factor. |
| A2 | `FX:*` are daily log returns; scenarios exponentiate. | Using simple returns double-counts convexity; large-shock scenarios become inconsistent (a −50% then +50% log round-trips; simple does not). |
| A3 | Flat cc zero curve per currency, ACT/365. | Curve-shape risk (FX swap basis, turn-of-year) invisible; forwards priced off a single node misprice long-dated points. Adequate at daily-VaR granularity only. |
| A4 | CIP holds in revaluation (forward = spot + deposits). | In stressed funding (2008, 2020 quarter-ends) the cross-currency basis widens: forward P&L needs a basis factor per ccy. |
| A5 | Square-root-of-time scaling to multi-day horizons. | Breaks for negatively skewed carry books (autocorrelated unwinds): 10-day VaR understated; use overlapping-window HS for the ICAAP number. |
| A6 | Sample/EWMA covariance is estimable and stationary within the window. | Regime breaks (post-peg) make the matrix garbage; EWMA recovers with lambda-half-life lag; the peg screen + stress add-on cover the gap (`edge_cases::ewma_covariance_reacts_faster_than_sample_after_regime_shift`). |
| A7 | i.i.d. scenarios within the HS window (plain). | Volatility clustering => Christoffersen independence failures; use FHS (implemented) — see VALIDATION.md. |
| A8 | Pegged currencies: history contains no break. | HS/parametric VaR ~= 0 on the peg. The engine *flags* (peg screen) and *prices* (jump-mixture, peg-break scenarios) this; ignoring the flag reproduces CHF-2015 blindness (`edge_cases::peg_break_jump_produces_loss_historical_simulation_misses`). |
| A9 | Bit-reproducibility relies on the crate-owned RNG (`rng::Rng`, xoshiro256++ seeded through SplitMix64) driving inverse-CDF transforms — never `rand::distributions::Normal` or any external-crate-defined stream. | Swapping in an external RNG crate silently breaks reproducibility of MC numbers across crate-version upgrades; it also reintroduces the dependency the crate deliberately avoids. |
| A10 | Linear (spot/forward) instruments only; options remain in the Python stack. | Option books need the GK layer: convexity/vega missing here. The compiled-leg design has a documented extension point (vol factor family), same as the C++ engine. |

## 5. Design choices worth defending

- **`Result` everywhere, no panics on user input.** Every public function
  that can fail on malformed input returns `fx_var_engine::Result<T>`
  rather than panicking; the only `panic!`/`assert!` calls in the crate
  guard genuine programming errors (e.g. `Rng::gamma`'s `shape > 0`
  precondition), matching the sibling `equity-var-engine` convention.
  Diagnostics (peg flags, Cholesky jitter) are returned in result structs,
  not printed — the caller decides the channel.
- **Refuse, never impute.** NaNs in histories, invalid alphas, empty
  books, non-monotone Cornish–Fisher moments and unfactorisable
  covariances all return `FxVarError::Invalid`/`Numerical` with actionable
  messages. An empty book errors rather than returning 0: a VaR of zero on
  a misloaded book is the most expensive silent bug in risk IT.
- **Jitter escalation on Cholesky** (1e-12·mean(diag), x10 up to 8
  tries, `matrix::Matrix::cholesky_with_jitter`), because singular
  covariances are *routine* FX inputs (two ccys pegged to the same
  anchor), with the jitter surfaced to the caller
  (`MonteCarloResult::cholesky_warning`).
- **Special functions from scratch** (Acklam+Halley inverse normal,
  incomplete gamma/beta, `src/stats.rs`): keeps the crate dependency-free
  and makes accuracy a *tested property* (< 1e-9 on the inverse CDF;
  Python-matched p-values to 1e-10) instead of an import.
- **Reused, not re-derived, primitives.** `matrix.rs`, `stats.rs` and
  `rng.rs` already existed as scaffolding when this engine's other modules
  were written; they are reused as-is rather than reimplemented, which is
  why the RNG here is xoshiro256++ (not C++'s `mt19937_64`) — the two
  engines are *functionally* equivalent (both feed a library-owned inverse
  normal CDF) but not *bit*-identical to each other, only internally
  self-consistent (fixed seed => fixed stream, within this crate).
