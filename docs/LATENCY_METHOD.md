# Latency method

**Software in-process latency, not wire-to-wire.**

Every latency number produced by `cpp/ull/` (and quoted anywhere in this
repository for that code) is the time between two reads of the CPU's
time-stamp counter inside one process. It does not include the network
card, the kernel's network stack, the switch, or the exchange. A
wire-to-wire figure needs a hardware capture point on both sides (a tap or
a NIC with hardware timestamps) and is not something this repository
measures or claims.

Numbers from a hosted CI runner or from a laptop under WSL2 are labelled
**shared-VM indicative**: the CPU is shared with other tenants and with a
hypervisor, so tails are inflated by events outside the code. The harness
records the CPU model and the hypervisor flag with every run so the label
is evidence-based, not a guess.

## 1. What is measured

`ull_latency_bench` (`cpp/ull/bench/latency_bench.cpp`) times, per call:

| Name | One call is | Notes |
|---|---|---|
| `book_apply` | apply one decoded QPBF message to the L3 book | closed loop |
| `decode_book` | decode one QPBF packet (8 messages) and apply them | closed loop |
| `decode_book_open_loop` | the same, scheduled at a fixed rate | reports service and response time |
| `ring_hop` | one SPSC ring hop between two threads | producer stamps, consumer records |

The input is pre-generated by the seeded QPBF generator before timing
starts, so generation cost is never in the measurement.

## 2. Reading the clock

Plain idea: read the counter, run the call, read it again, and stop the CPU
from moving instructions across either read.

Formal statement, x86-64 (`cpp/ull/bench/tsc.hpp`):

- start: `lfence; rdtsc; lfence`
- stop: `rdtscp; lfence`

`rdtscp` waits until all earlier instructions have executed before reading
the counter; the trailing `lfence` keeps later instructions from starting
before the read. The leading `lfence` on the start side does the same for
code before the call. This is the pattern in G. Paoloni, "How to Benchmark
Code Execution Times on Intel IA-32 and IA-64 Instruction Set
Architectures", Intel white paper 324264 (2010), with `lfence` in place of
`cpuid`, which Intel's SDM (vol. 2, LFENCE and RDTSCP) documents as
sufficient for ordering the read.

Ticks become nanoseconds through a rate calibrated against
`std::chrono::steady_clock` over 200 ms at start-up. That is only valid
with an invariant TSC; the harness reads `constant_tsc` and `nonstop_tsc`
from `/proc/cpuinfo` and records them.

Worked example: on the development laptop (Intel Core 5 120U, WSL2) the
calibration gave 2.496 ticks per nanosecond. The start/stop pair has its
own cost, which this harness does not subtract, so very small results are
at the floor of the method rather than the cost of the code.

One run on that laptop (2026-11-03, pinned to CPU 2, 1e6 calls, shared-VM
indicative, no huge pages, busy-poll 0), nanoseconds:

| Name | p50 | p99 | p99.9 |
|---|---:|---:|---:|
| book_apply | 219 | 671 | 1228 |
| decode_book (8 messages) | 1589 | 3811 | 82820 |
| ring_hop | 288 | 8.3e6 | 2.4e7 |

The ring-hop tail is the WSL2 hypervisor descheduling the second vCPU, not
the ring; it is the clearest example of why these numbers are labelled
indicative. Running the open-loop case at 1e6 packets/s, above the
measured capacity of about 6e5 packets/s, sent response time to 0.1 s
while service time stayed near 1.5 µs: the queue, not the code, is what a
closed-loop benchmark would have hidden. The default rate is now 2e5.

## 3. Histogram

`cpp/ull/bench/histogram.hpp` re-implements the HdrHistogram layout (Gil
Tene, HdrHistogram, hdrhistogram.org): exact counts below 2048 ticks, then
each power of two split into 1024 equal buckets. Every value is kept to
within 1/1024 of itself, from 1 tick to 2^63, in a fixed array allocated
once. Percentiles use the nearest-rank definition and report the top of the
bucket, so a reported percentile is never below the true one.

Evidence: `histogram_matches_exact_percentiles` in
`cpp/ull/bench/tests/test_bench.cpp` compares p50 through p99.99 with an
exact sorted array over 200,000 log-uniform samples; the worst relative
error is 0.00043 (bound 1/1024 = 0.00098), and no percentile is below the
exact value.

## 4. Coordinated omission

Plain idea. A loop that calls, times, and calls again never issues the
calls a real feed would have sent while one call was stuck. Those calls
never record their wait, so the tail looks better than any user would see
it. Gil Tene named this coordinated omission ("How NOT to Measure Latency",
Strange Loop 2015 and earlier talks).

Formal statement. The open-loop harness (`cpp/ull/bench/harness.hpp`)
gives call `i` an intended start `t0 + i T`. It records

- service time = end - actual start (what the code took), and
- response time = end - intended start (what a sender at rate 1/T saw).

A stall of length D delays the next D / T calls; call `j` after the stall
waits about D - j T.

Worked example, which is also the acceptance test
(`stall_injection` in `test_bench.cpp`): T = 2 µs, a 1 ms stall injected on
every 2000th call (0.05 % of calls), 400,000 calls.

| Statistic | Expected | Measured on the laptop (one run) |
|---|---|---|
| service samples >= 0.9 ms | exactly the 200 injected | 200-201 |
| service p99.9 | well below 1 ms (stalls are 0.05 %) | 0.2-0.6 µs |
| service p99.99 | about 1 ms | 1001 µs |
| response samples >= 0.1 ms | 450 / 2000 = 22.5 % from the stalls alone | 25-37 % |

The service histogram shows each stall once, at the right rate. The
response histogram shows the queue behind it; the extra above 22.5 % is
other preemption on a shared machine, which is exactly what response time
is meant to expose. At a stall rate of 0.2 % (every 500th call) the stall
moves inside service p99.9, as the second half of the test checks.

## 5. The machine, read back

Asking for a setting is not evidence that it took effect. `sysinfo.hpp`
reads back from the kernel, and the bench prints, for every run:

| Field | Source |
|---|---|
| CPU model, TSC flags, hypervisor flag | `/proc/cpuinfo` |
| CPU affinity in effect | `sched_getaffinity` after any pinning request |
| pinned (true only if the read-back mask is exactly the requested CPU) | `sched_setaffinity` then `sched_getaffinity` |
| transparent huge pages mode | `/sys/kernel/mm/transparent_hugepage/enabled` |
| huge page pool, huge pages backing this process | `/proc/meminfo` `HugePages_Total`, `/proc/self/smaps_rollup` `AnonHugePages` |
| socket busy-poll | `/proc/sys/net/core/busy_poll`, `busy_read` |
| CPU frequency governor | `/sys/devices/system/cpu/cpu0/cpufreq/scaling_governor` |

A field that cannot be read is printed as `unavailable`, which is itself a
finding (WSL2, for example, exposes no cpufreq governor). The development
laptop reports THP `madvise`, no huge page pool, busy-poll 0 and
hypervisor yes; numbers from it are therefore shared-VM indicative, with
no huge pages and no busy-poll in effect.

## 6. What a number on this page does not mean

- It is not wire-to-wire, and not tick-to-trade.
- It is not comparable with a vendor's published figure unless the vendor
  measured the same span with the same clock method.
- A shared-VM indicative p99.9 says more about the host than the code.
  Compare runs on the same machine, same build, same pinning, and look at
  differences, not absolute values.
- The QPBF load is synthetic (`docs/QPBF.md` section 11); real feeds have
  burstier arrivals.

## 7. Correctness gates that come with the timing code

| Gate | Test |
|---|---|
| No allocation on the hot path (ring, decode, arbitration, gap buffer, book, histogram) | `ull_noalloc_test` replaces global `operator new` and counts: 0 during the hot loop |
| SPSC ring has no data race | `ull_ring_tsan` (ThreadSanitizer); `cpp/ull/ring/genmc/spsc_genmc.c` for GenMC model checking under RC11 |
| Decoder never crashes on malformed input | mutation fuzz in `ull_qpbf_test`, ASan/UBSan build `ull_qpbf_asan`, libFuzzer target `ull_fuzz_decode` |

## 8. Reproduce

```
cmake -S cpp/ull/bench -B build/ull -DCMAKE_BUILD_TYPE=Release
cmake --build build/ull -j
ctest --test-dir build/ull --output-on-failure -LE long
ctest --test-dir build/ull -L long            # 1e8 round trip
build/ull/ull_latency_bench --cpu 2 --cpu2 3 --calls 2000000 --rate-per-s 1000000
```
